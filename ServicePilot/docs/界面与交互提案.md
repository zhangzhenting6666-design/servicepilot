## 1. 页面结构

建议单页、中文界面：顶部产品与模拟说明，中部聊天与执行事件，底部输入。桌面端聊天区约占三分之二，事件区约占三分之一；窄屏把事件区收为可展开面板。优先保证消息和输入可读。

```text
ServicePilot · 模拟电商售后                     [新会话]
仅使用演示订单与模拟规则；不执行真实退款。
原型预览时另显示：交互演示，回复与事件为预设样例。
┌─────────────────────────┬────────────────────┐
│ 聊天                    │ 执行事件           │
│ 初始提示 / 用户输入     │ 按请求分组         │
│ 客服回复 / 当前进度     │ Agent 转交与工具结果│
├─────────────────────────┴────────────────────┤
│ [输入你的问题，例如：我的订单 A1001 到哪了？] │
│ Enter 发送 · Shift+Enter 换行         [发送] │
└──────────────────────────────────────────────┘
```

- 初始提示：“可以查询演示订单或了解模拟售后规则。”
- 三个示例入口：“查询 A1001”“了解退货规则”“没有订单号怎么办”。点击只填入输入框，用户可修改后发送。
- 固定说明：“订单号示例：A1001。模拟退货规则需人工审核；本 Demo 不直接执行退款。”
- 不提供订单列表、退款按钮、登录入口或部署入口；本轮不设计 P1 模拟工单确认流程。
- 拟用浅色背景、单一强调色；错误同时带文字说明，不仅依靠颜色。按钮和事件展开可用键盘操作，焦点清晰可见。

## 2. 操作与反馈

| 用户操作 | 建议的界面反馈 | 行为边界 |
| --- | --- | --- |
| 输入并发送问题 | 保留用户消息，显示“正在处理…”；完成后追加客服回复 | 只把实际返回的答复显示为运行结果 |
| 发送空白内容 | 不发请求；提示“请输入问题” | 不生成空消息 |
| 等待回复 | 发送按钮暂时禁用；输入框仍可编辑下一条草稿 | 每个会话暂建议仅允许一个请求处理中；不自动排队发送 |
| 客服追问订单号，用户补充 A1002 | 两条输入留在同一会话；显示本轮回复与事件 | 多轮接续依赖后续后台会话能力，前端不自行补订单事实 |
| 用户更正订单号 | 原消息保留，按新消息继续处理 | 由后台采用新编号；不让前端静默替换旧消息 |
| 展开执行事件 | 显示该次请求的 Agent 转交、工具名和结构化结果摘要 | 不显示模型私有推理或虚构的执行过程 |
| 点击“新会话” | 无历史且无请求时直接进入空会话；否则提示“开始新会话后，当前聊天将从页面清除”，提供“取消 / 开始新会话” | 清空聊天、事件、输入与追问上下文；后台也须创建独立会话 |
| 在处理中确认新会话 | 进入新会话并提示“已开始新会话” | 旧请求即使晚到也不得写入新会话；不声称已取消后台执行 |
| 请求故障后点击“重试” | 对同一问题发起一次新尝试，分别保留两次事件 | 不无限重试；最终提交状态不明确时，先确认是否仍在处理，避免重叠请求 |

“新会话”的提示只描述页面与上下文行为，不声称删除运行日志或外部数据。重置过程若失败，保留旧会话并提示“新会话未能创建，请重试”，不显示成功。

## 3. 加载、空数据与错误状态

以下为建议文案；示例回复用于评审，接入后以工具事实与实际回复为准。

| 状态 | 聊天区反馈示例 | 事件区与下一步 |
| --- | --- | --- |
| 新会话为空 | “从一个问题开始，例如查询 A1001。” | “发送问题后，这里显示执行事件。” |
| 请求处理中 | “正在处理…”；消息旁有加载提示 | 仅在收到真实事件时追加，不预演转交或工具调用 |
| 处理完成但未提供事件 | 正常显示实际回复 | “本次未提供执行事件”；不等同于没有调用工具 |
| 缺少订单号 | “请提供订单号，例如 A1001。” | 保持会话，等待补充；不伪造查询事件 |
| 格式错误 | “订单号应为 A 加四位数字，例如 A1001。请核对后再发送。” | 实际调用工具时展示 invalid_input；未调用则不补造事件 |
| 查无订单 | “未找到 A9999，请核对订单号。” | 展示 query_order / not_found；用户可发送更正编号 |
| 待发货，无物流信息 | “模拟订单 A1002（台灯）待发货，暂无物流信息。” | 展示成功查询；缺物流不算错误，不填占位运单号 |
| FAQ 未收录 | “模拟规则中未找到相关说明，建议联系人工确认。” | 展示 lookup_faq / no_match；不编运费、到账时间 |
| 业务工具不可用 | “当前无法查询订单，请稍后重试，或联系人工。” | 展示 unavailable 或实际工具异常；不能显示旧查询结果冒充本次结果 |
| 请求连接失败或服务异常 | “本次未能取得回复。”；允许恢复后重试 | 显示可理解的错误；无实际工具事件则不说工具失败 |
| 返回为空或不符合接口约定 | “未收到可展示的回复，请重试。” | 标记响应异常；不将空白当作成功客服消息 |
| 退款请求 | “本 Demo 无法直接退款；是否通过需要人工审核，建议联系人工处理。” | 只展示实际订单查询与 Agent 转交；不显示“已退款 / 已转人工 / 已建工单” |

聊天容器在用户停留底部时跟随新消息；用户上翻历史时保留位置并提示有新消息。处理完成后恢复发送能力，保留等待期间编辑的草稿。中文输入法选字期间按 Enter 不发送。

## 4. 执行事件设计

事件按用户请求分组，顺序来自实际运行记录。默认展示可理解的摘要，工具状态码放在展开详情里。

- Agent 转交：“任务转交：Triage → Order”或“Triage → FAQ”。详情明确这是内部 Agent 切换，不是人工客服接入。
- 工具调用：“查询演示订单 · A1001”。只有收到调用开始事件才显示“查询中”；如果后台只提供最终结果，则直接展示最终记录。
- 工具结果：成功、输入需更正、未找到、暂不可用分别显示。成功摘要可含商品、状态、承运商、运单；仅展示工具返回的字段。
- FAQ 结果：成功时显示实际政策编号与内容摘要；编号缺失时不编造编号。
- 原型中所有事件显著标“预设样例”；未来运行界面只展示实际事件，不用动画模拟执行证据。
- 不展示 API 密钥、完整服务异常堆栈或模型私有推理。错误详情优先提供可定位本次请求的标识。

评审样例：发送“我的订单 A1001 到哪了？”→ 等待 → 样例内部转交 → 样例 query_order 返回 ok → “模拟订单 A1001（蓝牙耳机）已发货，承运商为模拟物流，运单号 MOCK1001。”该样例没有预计送达日期，不是已完成的电商实测证据。

## 5. 后续给开发对话的接口需求

此处是语义约定提案，不是现有 API 文档。路由地址、传输方式、超时与重试策略由开发根据已实现行为确定；本轮不假设支持流式回复。

| 界面需要的数据 / 能力 | 用途与验收点 |
| --- | --- |
| 独立会话标识、创建新会话结果 | 重置成功才切换；新会话不继承旧订单与追问上下文 |
| 每轮请求标识、请求所属会话 | 关联回复与事件；隔离晚到的旧会话结果 |
| 最终回复文本、请求完成或错误结果 | 正确结束加载；区分传输故障、响应异常与业务结果 |
| 实际 Agent 转交事件 | 包含来源与目标；不推测具体转交路径 |
| 实际工具事件 | 工具名、必要输入、状态、结果摘要、事件顺序；有开始/结束状态才展示进度 |
| query_order 和 lookup_faq 的 PRD 结果状态 | 区分 invalid_input / not_found / no_match / unavailable 与 ok |
| 事件来源与演示模式 | 原型样例与实际运行有明确标识，不能混用 |
| 请求状态查询或明确的重试语义（如需） | 网络断开但原请求仍处理时，避免重复提交；开发交接时明确支持程度 |

后台业务规范化订单号；界面保留用户原文，避免自行解析订单后绕过 Agent。界面不从静态样例补齐实际运行中缺失的业务事实。
