## 2. 为什么看到的代码只有几十行

当前保留的航空 main.py 为 225 行，原来将角色、工具、数据、交接、循环与显示放在一个文件。电商版本重新组织业务模块，单个短文件不代表整个程序只有这么多行。

| 文件 | 核对时行数 | 职责 |
| --- | --- | --- |
| servicepilot/order_tools.py | 39 | 参数化订单查询、状态返回、SDK 工具适配 |
| servicepilot/order_data.py | 41 | 从模拟 JSON 取数据并校验记录，保留可替换数据源接口 |
| servicepilot/agent_config.py | 44 | Triage / Order 的说明、可用工具与双向交接 |
| servicepilot/session.py | 85 | Runner 执行、历史与当前 Agent、真实事件记录 |
| scripts/run_order_customer_service.py | 176 | DeepSeek 连接、终端输入、运行模式与证据保存 |

这五个文件合计 385 行，还没有包括独立数据、验收组织和测试。行数不是质量指标；此统计只用来说明比较范围不能是“一个订单函数”对“整个航空示例”。后续文件增长后数字会变化。

## 3. 实际复用了什么、改写了什么

| 原航空示例 | 当前电商实现 | 关系 |
| --- | --- | --- |
| Agent 的 instructions / tools | agent_config.py 的业务角色与绑定 | 复用 SDK 配置方式，工作说明按新业务改写 |
| Triage 与专员之间 handoff | Triage 与 Order 之间 handoff | 沿用交接模式，业务目标替换 |
| 本地 FAQ / update_seat 函数 | query_order + 模拟 JSON | 新写电商只读工具，不是把选座函数改个名字 |
| Runner.run | session.py 的 Runner.run | 继续使用同一个 SDK 调度器，没有自写框架 |
| result.to_input_list / result.last_agent | session.items / session.current_agent | 沿用历史与最后 Agent 的接续逻辑 |
| 模型连接与输入 | 产品入口复用已接入的 DeepSeek 常量、隐藏密钥输入等辅助能力 | 新入口分别组织运行与记录，不从航空业务定义导入电商 Agent |

实际方式是“保留航空基线，借鉴原示例的配置与工作流模式，复用 SDK 和接入辅助，单独组织电商业务”。不是在原航空 main.py 上原位改完全部功能，也不是逐行复制原文件。不得在作品说明中把新电商模块描述为原示例未修改的功能。

## 5. 第二小批的完成条件

### C01 模拟政策查询

新增模拟政策数据，定义政策编号与内容。按 PRD 仅说明“签收后 7 天内可提出退货申请，是否通过需人工审核”；没有定义的运费、退款到账时间不提供。
lookup_faq 接受问题或政策类别，返回 ok / no_match / unavailable，成功时带政策编号和内容。
FAQ Agent 要实际请求工具后回答，不仅在指令里写政策就宣布查询功能完成。

### C06 同一会话切换

新会话先问“签收后几天内可以申请退货？”，再说“再查一下 A1001”。
两轮共享会话；第一轮实际 lookup_faq，第二轮实际 query_order(A1001)，最终订单事实与模拟记录一致。记录实际路由，不用预设箭头代替。
建议交接配置沿用原示例：Triage 可转 FAQ 或 Order，两个专员均可转回 Triage。

如果改变工作流配置、会话或工具，需要核对之前已通过的受影响行为；回归通过和两条新案例复核后，才将核心进度更新为 8/8。UI 留到这批完成后。
