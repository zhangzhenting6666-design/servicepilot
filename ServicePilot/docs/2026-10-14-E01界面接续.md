## 第一步：收敛能力文案，保留原验收记录

实际 C06 的 FAQ 最后一句提出“查询具体订单的签收时间”，订单工具没有签收时间字段。
这项未实际提供签收日期，不改写或撤销已记录的核心通过结果；作为进入界面前的独立质量项修正。

- FAQ 和 Order 的主动建议只覆盖支持的商品、订单状态、模拟承运商/运单与模拟退货申请政策。
- 当前没有签收时间、预计送达时间、运费或退款到账记录，不能承诺查询这些信息，也不能据订单状态推断签收时间或是否符合退货申请期限。
- 先调整最小必要的工作说明与能力文案，不为了消除提示而伪造新数据字段。
- 真实核对 C01/C06 和“帮我查 A1001 的签收日期”的边界答复，按实际改动做必要回归；保留新版本、工具事件和最终答复。未收录政策的真实扩展观察可验证“退货运费谁承担？”，工具应 no_match，不能编政策，不计入八条核心的分母。
- 如果这项尚未验证，记录待完成，页面不得声称支持签收时间查询。

## 第二步：沿用已有提案，实现最小 Streamlit 页面

方案依据《界面与交互提案.md》与《2026-10-13-界面阶段后台交接.md》。优先做真实运行页面，设计对话可细化视觉，开发对话负责唯一代码写入；不再创建多套后台。

| 页面区域 | 本轮功能 |
| --- | --- |
| 顶部 | ServicePilot 名称、模拟数据说明、新会话 |
| 聊天区 | 用户消息、真实模型答复、缺信息追问 |
| 输入区 | 中文问题输入与发送；空白不请求，重复发送受控 |
| 执行事件 | 真实 Agent 交接、工具名、必要参数、结果状态与摘要 |
| 状态反馈 | 空会话、正在处理、完成、请求失败、未找到和工具不可用 |

直接复用 OrderSession.ask(question)，页面适配层接收返回值并显示，不从页面硬编码答复或业务事实。status=completed 是运行完成，tool result 的 no_match/not_found/unavailable 仍是各自业务结果；failed 才是运行异常。首次页面可以非流式回复：等待时显示“正在处理”，完成后显示已有真实事件，不预演转交或查资料动画。
仅补必要的界面依赖及版本记录。模型仍 DeepSeek，本地模拟事实不变。CLI 入口、航空参照和已保存证据保留。

## 第三步：验证会话与页面，不止看外观

- 每个页面会话有独立 OrderSession；新会话重建历史和当前 Agent，不能只清空聊天文字。两个页面会话不能共享订单上下文。
- 同一会话一轮处理中不重复提交；若支持处理中重置，旧响应不得写入新会话。首版若不能支持，应明确禁用该操作，作为与原提案的交互差异记录，不假装已取消后台运行。
- 密钥仅在本机安全输入，不出现在页面正文、代码、运行证据或 Git；新增 Web 输入方式与当前 CLI 输入分别说明。
- 先从页面走订单查询、两轮补充与 FAQ→订单切换，再在页面入口复核首批全部 C01–C08。C08 故障只注入测试会话，不破坏正常文件。
- 检查事件与实际结果一致，显示未找到与服务故障的不同提示，重置与会话隔离、重复提交、中文输入与窄屏。离线页面检查和真实模型结果分别记录。
- 给出可启动命令/启动器、依赖、地址、实际截图、版本和证据；本地可用不等于已部署或他人设备已验证。

E-01 的完成标准是可实际操作、能调用现有模型和工具、会话与错误反馈正确、页面与后台事件一致；不是只生成漂亮静态图。
