## 1. 产品目标

ServicePilot 是一个基于 OpenAI Agents SDK 的模拟电商售后客服 Demo，帮助用户查询订单、了解售后规则，并在信息不足或需要人工处理时明确下一步。

本项目用于展示 Agent 产品经理的需求拆解、流程设计、工具边界、效果评测与迭代能力，兼顾 Python 实现能力。参考官方航空客服示例，个人改造点为电商订单工具、售后规则、多轮补充、异常处理与评测。没有做过真实用户访谈，以下痛点属于待验证假设，不代表调研结论。

## 2. 用户与场景

| 用户 | 典型请求 | 预期价值 |
| --- | --- | --- |
| 模拟买家 | 我的订单 A1001 到哪了？ | 获得与订单记录一致的状态 |
| 模拟买家 | 收到商品后几天内可以申请退货？ | 获得来源明确的模拟售后规则 |
| 模拟买家 | 我要退款，但不知道订单号 | 被引导补充信息或联系人工，知道下一步 |
| 演示者/评审者 | 这个回答如何产生？ | 查看实际路由、工具调用与结果，理解实现边界 |

以上是代表性场景，不是限定只能询问这些句子的列表，也不是“三次问答”的次数限制。同一任务可有不同表达，例如“我的订单 A1001 到哪了？”与“A1001 发货了吗？”；目标是识别请求并查询工具事实，而不是匹配整句后输出固定答案。会话应支持继续提问、补充信息、更正订单号和切换任务，具体能力通过案例验证。

痛点假设：重复 FAQ 占用客服时间；订单回答容易缺少事实依据；信息不完整时用户需要反复描述；自动客服可能越权承诺退款。

## 3. 首个可演示版本范围

| 优先级 | 需求 | 验收标准 |
| --- | --- | --- |
| P0 | FAQ 查询 | 使用模拟 FAQ 工具；未收录问题明确表示没有依据，不编造规则 |
| P0 | 模拟订单查询 | 按有效订单号调用工具，答复与返回值一致 |
| P0 | 缺失信息追问 | 没有订单号时追问；用户补充后继续完成查询 |
| P0 | Agent 分工与切换 | Triage 将 FAQ/订单任务交给对应 Agent；同一会话允许切换任务 |
| P0 | 会话管理 | 用户更正订单号后采用新值；新会话不继承旧会话信息 |
| P0 | 异常处理 | 格式错、查无订单、工具失败分别有明确提示，不虚构查询成功 |
| P0 | 人工边界 | 退款及规则外请求说明需人工审核或建议联系人工；没有真实人工接入通道，不声称已退款/已提交人工 |
| P0 | 运行与评测证据 | 本地可运行；记录工具事件；形成 25 条案例与实际结果 |
| P1 | 简洁 Web 界面 | 聊天、重置会话、模拟标识、执行事件展示 |
| P1 | 用户明确确认后创建模拟工单 | 确认前不创建；取消不创建；同一请求重复确认不重复创建；模拟工单不代表已接通真人客服 |
| P1 | 单/多 Agent 对比 | 同工具、规则、模型、参数和案例比较，记录实际结果 |

非目标：真实电商或支付系统、真实退款、用户身份认证、MCP、完整 RAG、复杂后台、生产级部署。本地使用固定模拟用户，不宣称实现真实订单访问权限管理。

## 4. 流程与职责

用户输入 → Triage Agent 判断任务 → FAQ Agent 或 Order Agent → 查询业务工具 → 根据工具结果答复。

- FAQ Agent 仅使用 FAQ 工具解释模拟政策。
- Order Agent 使用订单工具查询；信息缺失先追问，不能凭模型记忆编订单。
- Triage Agent 负责转交和任务切换，不替工具生成订单事实。
- 退款请求可查询相关订单、说明模拟规则并建议人工处理；当前版本没有退款执行工具。
- 工具查询失败时明确当前无法查询，建议稍后重试或联系人工，不无限重试。
- 若实现工单：先展示订单号、问题摘要和“模拟工单”提示，得到明确确认后创建。工具层校验确认状态与去重，不能只依靠模型指令。

采用多 Agent 是为了学习职责隔离与流程编排；不预设其效果或成本优于单 Agent，结论由后续实验支持。

## 5. 模拟业务约定

以下为本项目人为设定的演示规则，不是实际商家政策：

- 订单号为 `A` 加四位数字，例如 `A1001`；忽略首尾空格并统一为大写。
- A1001：蓝牙耳机，已发货，承运商“模拟物流”，运单号 MOCK1001；不提供未经记录支持的预计送达时间。
- A1002：台灯，待发货，尚无物流信息。
- A1003：键盘，已取消。
- A9999：格式有效但不存在。
- 模拟售后规则：签收后 7 天内可提出退货申请，是否通过需要人工审核；运费和退款到账时间未定义，不承诺。
- 用户说“立即退款，不用审核”，系统仍需说明人工审核边界，不能绕过规则。
- 测试模式可注入订单查询故障；故障与“查无订单”必须是不同结果。

## 6. 工具约定

| 工具 | 输入 | 结果约定 |
| --- | --- | --- |
| `query_order` | 订单号 | 状态：ok / invalid_input / not_found / unavailable；成功时返回订单事实 |
| `lookup_faq` | 用户问题或政策类别 | 状态：ok / no_match / unavailable；成功时返回政策内容与政策编号 |
| `create_mock_ticket`（P1） | 订单号、摘要、确认状态、请求标识 | 工单编号；未确认则拒绝；同请求重复执行返回原工单 |

最终答复用自然语言解释结果，工具状态码保留在事件记录中。日志只保存实际运行事件，不展示模型私有推理。订单更新、退款执行不在工具权限范围内。

## 7. 评测与完成标准

开始改造前先确认 8 条核心验收案例；核心闭环稳定后再扩充至 25 条，预先分为 15 条开发集和 10 条留出集。案例覆盖 FAQ、订单、多轮、异常和人工边界。8 条和 25 条是检查产品行为的案例数量，不是运行时可问的问题或对话轮数上限；预期规定业务事实与处理行为，不要求客服回复逐字一致。

评测记录：输入步骤、预期行为、实际答复、工具/路由事件、通过与否、失败原因、版本、运行模型、耗时；有 usage 才报告 token 或成本。

- 进入界面阶段前：8 条核心案例均达到各自预期。
- 最终报告：如实给出成功案例数与分母，分别报告开发集和留出集，不编造效果提升。
- 错误订单事实、越权承诺退款、会话混用属于阻断演示的问题，需要修复或明确限制相关功能。
- 交付：可运行 Demo、PRD、工作流、评测报告、README、演示录屏和个人贡献说明。

## 9. 后续扩展原则（设计约束，尚未实现）

2026-10-13 第二小批完成状态：模拟 FAQ、订单与首批多轮/异常/边界八条在 b438a4c 同一版本上实测通过，正式结论见 artifacts/orders/d01-batch2-review-2026-10-13.json。历史状态段落保留；这不是任意问法的效果结论，25 条评测、UI、真实业务接入与真实人工通道未完成。当前订单没有签收时间字段，实测中 FAQ 主动建议查询该字段的文案观察已记录，不计已实现能力。此补充只同步状态，未改变 v0.2 业务规则。

- 分开组织 Agent 配置、业务工具、模拟数据、会话逻辑与界面，不把问题原句、数据和回复全部写成固定的一问一答。
- 工具使用参数化查询和结构化状态。新增模拟订单或政策优先扩充数据；未来替换为数据库或业务接口时，尽量保持工具对 Agent 的输入与结果约定稳定，仍需实现和重新验收。
- 多轮会话保留必要历史和业务状态。长会话后续需要上下文容量、成本、超时与每轮内部执行次数管理；不宣称可无限轮、无限记忆，也不把内部执行上限误当成用户只能问三次。
- 表达变化通过同意图改写、模糊输入、编号更正和场景切换案例检验，不能因接入模型就认定全部表达都能正确处理。
- 新业务先补需求、工具权限、结果状态和验收，再判断是否需要新增 Agent；扩展不等于不断增加 Agent 数量。真实业务接入所需身份与权限、真实人工通道、退款执行等属于另行设计的后续范围。
- 首版能处理的是定义好的订单与政策能力。事实未提供或请求超出能力时，明确不足并给出下一步，不为丰富回复虚构信息。
