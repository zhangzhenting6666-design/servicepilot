## 1. 建议怎样整合

把“项目学习”与“代码展示”结合：从实际代码中选片段，先讲清楚，再写成可公开阅读的解读；开发沿现有视觉接入第四栏和外层自适应。配色优化单独接续，等用户学习并提供参考后再由界面设计提取风格，不作为第四栏开发的前置条件。此前已交付首版继续作为基线。

已确认四栏：**客服体验 / 架构总览 / 项目介绍 / 代码解读**。前三栏内容、位置、内部布局与交互保持，新增第四栏。

| 栏目 | 回答访客的问题 | 主要展示 |
| --- | --- | --- |
| 客服体验 | 我能用它做什么？ | 实际问答、当前工具事实与事件 |
| 架构总览 | 整体怎样运转？ | UI、会话、Runner、模型、Agent、工具、数据的关系 |
| 项目介绍 | 为什么做、本人参与什么、怎样验证？ | 场景、产品决策、真实截图、评测范围与个人贡献 |
| 代码解读 | 这些行为具体怎样实现？ | 选定源码片段、解释、设计理由与对应证据 |

“页面有代码”本身不等于个人已掌握。展示重点应是本人能复述输入/输出、职责划分、设计取舍和失败路径；按实际理解描述，不增加未经确认的独立开发经历。

## 2. 搜索到的参考案例

以下为官方案例或文档，借鉴表达方式，不意味着本项目已经使用相应产品：

1. [Streamlit st.echo](https://docs.streamlit.io/develop/api-reference/text/st.echo)：将代码与其执行结果一起展示。可借鉴“片段与效果邻近”的讲解方式。st.echo本身会执行代码，本项目公开解读栏首版应只展示，不因此触发模型调用。
2. [Langfuse官方示例项目](https://langfuse.com/docs/demo)：交互、产生trace、查看对应执行记录。可借鉴从一个用户问题追踪工具/模型行为；本项目已有事件记录，不需要为该栏目新增Langfuse依赖。
3. [marimo代码与交互组件示例](https://marimo.io/features/feat-widgets)：代码、交互和输出关联。可借鉴解释与反馈相邻的排版，不迁移技术栈。
4. [Streamlit st.code](https://docs.streamlit.io/develop/api-reference/text/st.code)：支持代码高亮、行号和代码块布局，可用于现有Streamlit应用的选定代码展示。

## 3. 第四栏的内容结构

每节采用：**一个业务问题 → 本节一句话结论 → 一段关键代码 → 重点解释与取舍 → 对应运行证据/来源 → 一个自测问题**。

建议每个默认可见片段约10–25行；长内容拆成步骤或折叠。代码来自真实文件，标识模块与对应快照/发布版本。行号、片段和说明在每次变更后同步核对，不手写与版本无关的永久行号。简化示意必须明确标注，不冒充运行源码。

| 主题 | 用户能讲清楚什么 | 源文件与内容 |
| --- | --- | --- |
| ① Agent如何分工和交接 | Triage为何分流，FAQ/Order能用什么工具，SDK执行什么 | servicepilot/agent_config.py：角色与tools/handoffs配置 |
| ② 模型怎样接入 | 客户端、服务地址、模型与RunConfig各是什么；使用同一模型不等于同一角色 | servicepilot/model_config.py：不包含密钥值的配置片段；密钥位置只作服务端说明 |
| ③ 查询为何有依据 | 订单号作为参数进入工具，格式校验后读取数据并返回结构化状态 | servicepilot/order_tools.py、order_data.py、data/orders.json的模拟记录 |
| ④ 多轮怎样接续 | 历史与当前Agent怎样更新，新会话为何不继承旧订单 | servicepilot/session.py、web_runtime.py的选定部分 |
| ⑤ 失败怎样反馈和验证 | 业务查无记录与模型API失败区别，案例结果如何对应版本 | session.py、workbench_ui.py及评测报告的指定证据 |

下午先把①②③作为学习与内容重点，④⑤可以先做精简解释再逐步展开；不要求一下午完成所有代码深度学习。

### 一节示例：为什么模型不会直接猜订单事实

- 问题：用户说“查一下A1001”，它怎样知道订单状态？
- 片段：query_order校验订单号、调用数据源、返回ok/not_found/unavailable的代码。
- 解读：模型负责提出调用，Runner执行Python函数，订单事实来自当次模拟JSON查询；展示数据与真实电商平台无关。
- 取舍：固定参数结构和明确返回状态，方便检查模型调用与最终回答是否一致。
- 证据：复用已保存、已标明日期和版本的工具参数/结果；不把历史事件显示为当前实时执行。
- 自测：把A1001换成A9999，正常结果是什么？与接口500有什么区别？

### 已确认新增：完整代码展示

在第四栏提供**“完整代码展示”折叠区**，默认收起；点击展开后按文件查看完整源码。它是折叠面板，不是需要重做顶层导航的另一页。

- 展开后先说明公开范围和版本，再提供文件选择下拉框、文件路径、代码行号与复制功能。
- “完整”指清单中公开产品文件的完整内容，不把截取的10–25行标为完整文件。使用说明列出包含与排除范围，不把第三方SDK依赖、虚拟环境或整个电脑目录算作项目源码。
- 清单覆盖应用入口、Agent配置、模型接入、查询工具、数据源、会话、展示与部署等公开产品模块；保留第三方来源说明。源码快照须对应本次实施/发布版本；若脱敏或省略，明确标注，不伪称原文完整。
- 阅读区可滚动；手机端代码在自身区域横向滚动，页面整体不横向溢出。选择文件、展开与复制均不执行代码、不调用API。
- 只读取确定的公开文件清单，不提供任意路径读取；Secrets、密钥值和原始运行日志不进入展示。原私有仓库无需改为公开。
- 本轮先做页面查看与复制，不额外增加整个源码压缩包下载要求。

建议页面关系：上半部“关键代码与解读”，下半部“完整代码展示（默认收起）”。这样默认易读，需要深入了解的人可以展开核对。

## 4. UI怎样优化

用户已纠正上一版建议：**仅做视觉风格调整，不重做栏目、页面结构、内容层次或交互。** 本节取代此前“重排首屏、重新组织执行轨迹、改变各页版式”的提议。

### A. 现在可做：外层自适应修正

用户截图显示品牌栏像居中的白色面板，页面上方有明显空隙，左右边距不是本次重点。本地CSS确有 `.stMainBlockContainer{max-width:1200px;padding:1.5rem 28px 2rem;}`，品牌与导航位于该内容范围内；具体顶部额外空白仍需结合实际Streamlit渲染核对。

- 让品牌/导航的顶栏背景横向延伸到网页可视区域边缘，减少顶部无意义空隙，形成连续的页面顶部。
- 正文仍保留合理阅读宽度；不是将聊天、文字与图片无限拉宽，也不改变聊天/事件双栏比例或内容顺序。
- 区分浏览器地址栏、Streamlit平台工具区和应用内容，不以删除所有平台控件实现“铺满”。修正后检查Share等平台入口与正文不互相遮挡。
- 不通过锁死100vh或禁止页面滚动来伪装全屏。长内容、代码、架构图仍能正常滚动与访问。
- 检查宽屏、普通笔记本、390px；只允许确有需要的代码/架构区域内部滚动，不出现页面级横向滚动。

### B. 等待用户参考：配色与视觉风格

用户会先学习UI并提供案例。收到后提取喜欢的背景、主色/强调色、文字对比、边框、阴影与代码高亮风格，先在同一现有布局做对照预览，再统一应用到四栏。用户无需现在先选颜色或再次确认旧方案。

当前保留浅色基线，但未来配色不预设必须为深绿，也不自动采用此前已撤回的深色/黄绿色方案。用户提供参考后按新参考判断。

不增加新业务功能、重组导航、改变按钮动作、迁移前端框架或加入无关装饰动效。用户这次说的“换风格”按换视觉表达执行。
