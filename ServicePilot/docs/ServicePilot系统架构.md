## 1. 总体关系

用户 → Streamlit 聊天界面 → Python 会话与应用逻辑 → Agents SDK / Runner。
Runner 使用当前 Agent 的配置请求 DeepSeek，根据模型输出执行 handoff 或工具；必要时继续请求模型。
业务角色为 Triage、FAQ、Order。FAQ 调用 lookup_faq，Order 调用 query_order。
工具访问本地模拟 FAQ / 订单 JSON，返回结构化事实与状态；模型据结果答复，Runner 返回最终结果。
应用保存接续历史与事件，页面展示真实答复与实际事件，并等待下一题。

## 2. 各层职责

| 层 | 组件 | 主要职责 |
| --- | --- | --- |
| 用户界面，P1 | Streamlit | 输入、答复、实际事件、新会话、模拟标识 |
| 应用与会话 | Python 应用逻辑 | 会话和请求标识、历史、当前 Agent、追问接续、隔离晚到结果 |
| 编排 | Agents SDK / Runner | 提供配置、请求模型、执行交接与工具、得到最终答复后返回 |
| 模型服务 | DeepSeek API | 按工作说明与工具定义提出动作或生成答复；多个角色可共用模型 |
| 角色 | Triage / FAQ / Order | 分流；政策查询；订单追问和查询 |
| 工具 | lookup_faq / query_order | 规范化输入、校验、查询、返回状态和事实 |
| 资料 | 本地 FAQ / 模拟订单 JSON | 唯一业务事实来源，不混同于对话历史 |
| 输出 | 应用与界面 | 展示答复和真实事件，保存接续信息，等待下一题 |

首版可由 Streamlit 与 Python 业务模块在同一应用中组织，不要求独立 HTTP 后台、云部署或数据库。
原图 search_faq() 是概念名称；本说明以 PRD 的 lookup_faq 为正式工具约定。两者不代表两个查询工具。
没有 SDK Agent；SDK 是程序库，Runner 是执行组件。航空 Seat Booking 是学习参照，不属于电商角色图。

## 3. 订单路径，目标示例

1. 页面收到“我的订单 A1001 到哪了？”，提交原文。
2. 应用记录消息与本轮标识，取出会话历史，调用 Runner。
3. 新会话的 Triage 使用模型判断订单任务，Runner 执行交给 Order 的 handoff。
4. Order 信息完整时请求 query_order；缺编号则追问并等待下一轮用户输入。
5. 工具规范化编号、检查格式、读取本地模拟数据，返回状态与事实。
6. 模型依据工具结果组织回答，不编送达时间，不承诺直接退款。
7. 应用显示答复与真实事件，保存历史与最后 Agent，等待下一题。

2026-10-13 已在 CLI 验证上述订单核心路径（不含页面），C02 与一种改写通过；Streamlit 输入与页面展示仍为目标设计。多轮及其余案例不能据单轮结果认定通过。

## 4. 多轮与交接设计建议

新会话从 Triage 开始；连续会话可沿用 last_agent 接续。
配置建议：Triage 可交给 FAQ 或 Order；FAQ 和 Order 遇到其他职责的问题可转回 Triage。
例如政策后查订单：FAQ → Triage → Order。
是否每轮重回 Triage 仍是入口策略选择，开发时须明确实现；不能从目标图推断已采用某个策略。
新会话清空历史、订单编号与追问上下文；用户更正编号使用新值；旧请求结果不得污染新会话。

## 5. 状态与操作边界

- query_order：ok / invalid_input / not_found / unavailable。
- lookup_faq：ok / no_match / unavailable。
- 模型服务失败与工具查询失败分开记录；不无限重试，不用旧数据冒充当前结果。
- P0 退款和规则外问题仅说明人工审核边界或建议联系人工，没有真实转人工通道、退款执行。
- P1 可增加 create_mock_ticket：先呈现订单号与摘要，经用户确认后创建；工具校验确认与去重；取消不创建。
- 模拟工单不等于真人接入，也不代表已退款。
