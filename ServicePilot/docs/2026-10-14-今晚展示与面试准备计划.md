## 网址方案

优先尝试 Streamlit Community Cloud，复用当前 Python/Streamlit 产品。官方支持从 GitHub 指定仓库、分支和入口，生成 streamlit.app 网址，并在平台配置 Secrets。依据：[部署说明](https://docs.streamlit.io/deploy/streamlit-community-cloud/deploy-your-app/deploy)、[Secrets 说明](https://docs.streamlit.io/deploy/streamlit-community-cloud/deploy-your-app/secrets-management)。账号、授权和用户所在网络的实际可达性仍需现场确认。

开发需要具体处理：

- 云端通过平台 Secrets 初始化现有后台，保留本机隐藏输入模式。不要让访客输入项目方 API 密钥，也不要把密钥写入仓库或客户端。
- 复查当前 web_version 的 Git 工作目录假设、版本识别、日志写入位置和 Linux 依赖；锁文件来自 Windows，不能直接宣称跨平台安装已通过。
- 仅整理发布所需应用文件、模拟数据和必要依赖，不整体上传个人工作区、历史对话、凭据或虚拟环境。发布前完成本地候选版本和文件清单，再进行平台发布。
- 为共享的真实 API 演示设置简单的访问或请求次数控制及并发上限；关闭故障注入入口。这是演示运行配置，不扩展电商登录体系。
- 云端不可用时显示明确状态；演示截图和历史记录必须标注，不作为新生成答复。

部署后的最小验收：外网设备或手机移动网络访问；A1001 实查；缺编号后补 A1002；政策转订单；A9999 查无记录；新会话与另一个浏览器会话隔离。检查页面刷新与服务重启后的可恢复启动。记录实际结果，不把本机旧 5/5 当作云端已经通过。

临时隧道可用于现场调试，但依赖本机服务，不作为简历上的长期作品入口；Cloudflare 官方也明确 Quick Tunnel 是临时地址且无可用性保证。依据：[Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)。

如果云端受账号、依赖或网络阻塞，先把具体阻塞和已尝试结果交回主线，及时决定改用已有可用托管平台还是保留本机演示。可公开访问的作品介绍页加真实录屏能作为备用展示，但它不等于可交互的 Agent 应用，简历必须标注入口性质。未得到真实网址前，不填写虚构地址或声称已部署。

## 今晚学习重点

以“我的订单 A1001 到哪了”为线索，依次看：页面提交 → OrderSession 组织历史 → Triage 分流 → Runner 执行 handoff → Order Agent 发起 query_order → Python 读取 JSON → 模型依据事实回答 → 页面显示实际执行事件。

需要理解：

- 三个 Agent 是配置的职责，SDK/Runner 是执行机制，DeepSeek 是模型服务，工具是本地函数，JSON 是模拟事实来源。
- 一次简单订单问题可能请求模型三次：Triage 选择交接、Order 选择工具、Order 根据工具结果回答；Python 工具执行本身不是另一次模型请求。次数取决于实际输出，不能按 Agent 人数固定计算。
- 多轮补充依赖保留的对话历史和当前 Agent；新会话须重建后台上下文。
- 查无订单、未收录政策和请求异常是不同状态；没有实际退款和人工接入。
- 评测固定样本的通过结果说明这些案例已检查，不能代表总体准确率或真实业务效果。

只深入两项有证据的开发问题：Triage 仅口头说转接时如何通过工具选择配置修正；Windows 保存证据遇到文件锁后如何进行有界磁盘重试。不会的实现细节先标记，由我结合代码解释，不能直接写成个人独立掌握或独立修复。
